## 2.5 中断屏蔽寄存器

这些寄存器控制异常能否激活，不清除外设中断源或已挂起状态，也不阻止 Reset。它们复位为 0；只能由特权软件有效访问，非特权读返回 0、写入无效。

| 寄存器 | 有效字段 | 功能 | 关键边界 |
|---|---|---|---|
| PRIMASK | bit 0 | 为 1 时阻止所有可配置优先级异常激活 | 不屏蔽 NMI、HardFault |
| FAULTMASK | bit 0 | 为 1 时阻止除 NMI 外的异常激活 | 能屏蔽 HardFault；风险高，不宜作为一般临界区工具 |
| BASEPRI | 组优先级阈值 | 非零时按 PRIGROUP 去掉子优先级部分，阻止相同或更低组优先级异常激活 | 值 0 表示不设置此屏蔽；数值越小紧急程度越高 |

F103 实现四个优先级位，写入优先级字节时有效值位于高四位，低四位未实现。CMSIS 的 `NVIC_SetPriority(IRQn, priority)` 接收未左移的逻辑优先级 0～15；`__set_BASEPRI(value)` 则直接写入寄存器编码，若从逻辑优先级换算，须先左移 4 位。例如，逻辑值 5 对应 BASEPRI 编码 `0x50`，不能把两种接口的参数直接互换。

PRIGROUP 是 SCB_AIRCR 中划分组优先级与子优先级的字段。BASEPRI 只按组优先级设限，不能在同一抢占组内按子优先级选择性放行；某异常即使未被屏蔽，也仍须满足使能及抢占当前执行优先级的条件，才能进入处理程序。

例如，PRIGROUP=5 时，高四位分为 2 位组、2 位子；写 BASEPRI=0x50 后，有效组阈值为 0x40，所以编码 0x40 和 0x50 的中断都会被屏蔽。建议阈值的子优先级位写 0，避免误读。

只有当前执行优先级数值大于−1时才能置 FAULTMASK=1，不能在 NMI/HardFault 中靠它进一步提升屏蔽。[Arm DDI0403E.b §B1.5.4，B1-584～585](../来源/Arm_DDI0403Eb.md#src-armv7m-eb-mask)

八字硬件栈帧不包含 PRIMASK、BASEPRI、FAULTMASK。异常返回不会从该帧恢复它们：PRIMASK、BASEPRI 保持返回时的当前值；FAULTMASK 则在从 NMI 以外的任何异常返回时自动清 0，从 NMI 返回时不自动清除。这一特殊清零规则不是“恢复进入前的值”。

临界区应保存进入前的屏蔽状态，并在退出时恢复，避免无条件开中断破坏外层临界区。嵌套的 BASEPRI 临界区还须保证进入时不削弱外层屏蔽：`MSR BASEPRI_MAX` 只接受能启用或增强屏蔽的非零值，不能用它解除屏蔽；退出时应把保存值写回 BASEPRI。

屏蔽也不是忽略故障：已使能的异步 IRQ 可保持挂起；同步故障或 SVC 若因当前执行优先级而不能抢占，且当前执行优先级低于 HardFault，会升级为 HardFault。FAULTMASK=1 时某些故障可导致锁死，不能把它当成安全执行任意危险访问的保护层。

## 3.2 内存类型与访问顺序

Normal 内存允许处理器为效率进行一定的访问重排或提前访问。Device 用于有副作用的寄存器，访问约束更严格，但写入可能经过缓冲。Strongly-ordered 的访问顺序和完成约束更强，写入不采用普通的缓冲语义。

实际使用时，片内代码区和 SRAM 属于 Normal，外设寄存器区属于 Device，包含 NVIC、SysTick、SCB 的 PPB（私有外设总线）区属于 Strongly-ordered。内存类型不改变各寄存器规定的访问宽度、对齐或读写副作用。

下表表示原文给出的顺序关系。“保证”表示前一访问与后一访问受该类型组合约束保持顺序；“未保证”不能作为设备协议的顺序依据。

| 前一访问类型 / 后一访问类型 | Normal | Device，不共享 | Device，共享 | Strongly-ordered |
|---|---|---|---|---|
| Normal | 未保证 | 未保证 | 未保证 | 未保证 |
| Device，不共享 | 未保证 | 保证 | 未保证 | 保证 |
| Device，共享 | 未保证 | 未保证 | 保证 | 保证 |
| Strongly-ordered | 未保证 | 保证 | 保证 | 保证 |

表中 Strongly-ordered→Normal 仍为“未保证”，对应 PM0056 Table 11 的“−”；不能把 Strongly-ordered 理解为与任意类型的访问都自动有序。“未保证”表示没有该类型组合的一般顺序保证，不代表处理器可以违反同一程序的数据依赖；若同步协议依赖访问顺序，应按协议加入适当屏障。

volatile 约束编译器对访问的处理，不能代替处理器内存屏障，也不能让多次访问成为一个原子事务。

来源：[PM0056 §2.2.1–2.2.4，Tables 11–12](../来源/PM0056.md#src-pm0056-r7-barriers)；[Arm DDI0403E.b §A3.7.2，A3-91～92](https://documentation-service.arm.com/static/5f8fef3af86e16515cdbf816#page=91)。

## 3.3 三种屏障

| 指令 | 保证的重点 | 常见用途 |
|---|---|---|
| DMB（Data Memory Barrier） | 屏障前后的显式内存访问按要求排序 | 发布共享数据后置标志、交接信号量、修改向量后开放使用 |
| DSB（Data Synchronization Barrier） | 等待先前显式内存访问及相关操作完成，再继续后续指令 | 改变影响执行的系统配置、进入要求写操作完成的状态 |
| ISB（Instruction Synchronization Barrier） | 刷新后续取指和执行上下文 | 修改 CONTROL、执行环境或代码后，使后续指令看到新状态 |

PM0056 §2.2.4 的五项具体用法为：

- 改向量项后、使能相应异常前插入 DMB，确保新向量先可见。
- 自修改代码后插入 ISB；若写入尚未完成，还应结合适当 DSB 完成写入与取指同步。
- 切换存储器映射后使用 DSB。
- 对已挂起或激活异常动态修改优先级后使用 DSB，确保修改生效。
- 多主设备信号量操作后使用 DMB，使共享数据访问按协议对其他主设备可见。

对 Strongly-ordered 区（例如 SCB）访问的既有顺序保证，不免除某一系统配置操作另外规定的 DSB/ISB，也不能推出它与前后 Normal 访问自动有序。内存映射、异常优先级等系统改变需要按相应寄存器说明使用 DSB/ISB；若需保证先前系统控制空间写入的上下文改变对后续指令可见，可用 DSB 后接 ISB。自修改代码须同时满足代码写入完成与后续重新取指，单独 ISB 不能替代数据访问完成屏障。处理器没有数据缓存也不意味着可以省略所有屏障。

DSB 等待的是架构规定的内存访问完成，不保证该次寄存器写入触发的外设内部操作已经结束，也不等待整项 DMA 传输完成。软件仍须检查相应外设状态或 DMA 完成标志；同样，关中断只改变 CPU 的异常处理条件，不会暂停 DMA。


来源：[PM0056 §2.2.4；§3.9.3–3.9.5](../来源/PM0056.md#src-pm0056-r7-barriers)；[Arm DDI0403E.b §A3.7.1，A3-90～91](https://documentation-service.arm.com/static/5f8fef3af86e16515cdbf816#page=90)、[§A3.7.3，A3-93～95](https://documentation-service.arm.com/static/5f8fef3af86e16515cdbf816#page=93)；[RM0008 Rev 21 §13.1、§13.4.1 DMA_ISR](https://www.st.com/resource/en/reference_manual/cd00171190-stm32f101xx-stm32f102xx-stm32f103xx-stm32f105xx-and-stm32f107xx-advanced-armbased-32bit-mcus-stmicroelectronics.pdf#page=274)。

## 6.4 异常进入与栈帧

[Arm DDI0337E §5.5.1 Figure5-1](../来源/Arm_DDI0337E.md#src-ddi0337e-stack-layout)给出下列栈布局；地址顺序不是压栈总线事务时间先后。

正常异常进入并成功压栈时，硬件把 R0、R1、R2、R3、R12、LR、返回 PC、xPSR 共八个 32 位字保存到异常发生前正在使用的堆栈。Reset 不按此流程保存被中断上下文；尾链或晚到异常也不会各自再建立一份相同的帧。按压栈后 SP（栈指针）起算的地址顺序如下：

| 偏移 | 保存值 |
|---|---|
| +0x00 | R0 |
| +0x04 | R1 |
| +0x08 | R2 |
| +0x0C | R3 |
| +0x10 | R12 |
| +0x14 | LR |
| +0x18 | 返回 PC |
| +0x1C | xPSR |

SCB_CCR.STKALIGN=0 时要求 4 字节对齐，为 1 时要求 8 字节对齐。若为满足 8 字节对齐而额外保留一个字，保存的 xPSR[9] 为 1，该填充位于帧的 +0x20 处，表中八个寄存器的偏移不变。因此，在帧完整且对齐状态有效时，$`SP_{\mathrm{before}}=SP_{\mathrm{frame}}+32+4A`$。式中 $`SP_{\mathrm{before}}`$ 是异常前 SP，$`SP_{\mathrm{frame}}`$ 是帧起始地址，两者均以字节地址表示；$`A`$ 是保存的 xPSR[9]，取 0 或 1，32 和 4 均表示字节偏移。硬件返回时据此恢复 SP，不能一律只加 32 字节。不要在异常进入和返回之间清除原先置 1 的 STKALIGN，否则可能破坏恢复。

进入 Handler（异常处理模式）后，活动栈使用 MSP（主栈指针）。若被中断的 Thread（线程模式）使用 PSP（进程栈指针），硬件帧仍在 PSP 上；故障入口需要依据入口 LR 的 EXC_RETURN 判定帧在哪个栈。这里的帧内 LR 是被中断代码的 LR，与异常进入时写入当前 LR 的 EXC_RETURN 不是同一个值。R4～R11 不属于这八字自动帧，普通编译器函数和 RTOS 负责按调用约定保存所需寄存器。

做故障取证时，应在 C 函数前导或子函数调用改变 SP/LR 之前捕获入口信息，再验证帧地址及长度是否落在该任务/主栈实际分配范围、地址是否可读、对齐是否正确。仅凭 EXC_RETURN 选对 MSP/PSP，不足以证明帧有效：

- 压栈故障 STKERR 表示 SP 已调整，但帧内容可能不完整，不能把其中 PC/xPSR 当成可靠现场。
- 出栈故障 UNSTKERR 表示原返回帧仍保留，失败返回不调整 SP、也不另压一份新帧；须分析原返回栈的访问失败。
- 栈越界或覆盖若仍落在可访问 SRAM，未必产生 STKERR/UNSTKERR。状态位为 0 不能代替栈边界及内容一致性检查。

异步异常请求到达与进入处理程序之间存在响应过程，不应以为触发后当前程序一条指令都不可能继续执行。

来源：[PM0056 §2.3.7](../来源/PM0056.md#src-pm0056-r7-exception-frame)；[§4.4.10 SCB_CFSR，STKERR/UNSTKERR](../来源/PM0056.md#src-pm0056-r7-fault-evidence)；[Arm DDI0403E.b §B1.5.7，B1-591～592](https://documentation-service.arm.com/static/5f8fef3af86e16515cdbf816#page=591)。栈边界检查是依据上述故障边界给出的工程要求。

## 6.5 尾链与晚到异常

若异常返回时已有满足激活条件的挂起异常，处理器可以进行尾链：跳过不必要的完整出栈和再次压栈，直接转入下一处理程序。

若处理器正在为一个异常执行进入压栈，而此时更高优先级异常到达，可以先服务晚到的高优先级异常；原来的较低优先级异常保持等待。软件不应依赖触发先后顺序替代优先级仲裁。

来源：[PM0056 §2.3.7](../来源/PM0056.md#src-pm0056-r7-exception-frame)。

## 6.6 EXC_RETURN

异常进入时，硬件在 LR 中写入 EXC_RETURN（异常返回编码）。它不是普通代码地址；处理程序若调用子函数，应按调用约定保存它。在 Handler 模式用受支持的返回指令将有效 EXC_RETURN 装入 PC 时，处理器按照编码执行异常返回，恢复硬件栈帧。

| EXC_RETURN | 返回目标 | 恢复帧使用的堆栈 |
|---|---|---|
| 0xFFFFFFF1 | Handler | MSP |
| 0xFFFFFFF9 | Thread | MSP |
| 0xFFFFFFFD | Thread | PSP |

EXC_RETURN[2] 选择恢复栈（0 为 MSP，1 为 PSP），bit[3] 选择返回模式（0 为 Handler，1 为 Thread）；必须使用表中的完整合法组合，不能只改某一位就假定能返回。BX、包含 PC 的 POP、以 PC 为目标的 LDR/LDM 可以触发返回识别。

合法编码也必须与当前异常状态及栈内容一致：

- 正在退出的异常必须处于 active（激活）状态。通常只有最后一个活动异常退出后才能回 Thread；SCB_CCR.NONBASETHRDENA=1 可放宽这一项检查，但不会取消其余有效性要求。
- 返回 Thread 时，帧内 xPSR 的 IPSR 异常号应为 0；返回 Handler 时应非 0。模式/活动状态或保留编码检查失败可置 CFSR.INVPC，触发 UsageFault。
- 帧内返回 PC 应为有效的半字对齐代码地址，xPSR.T（bit 24）须为 1，以恢复 Thumb 执行状态。栈中的返回 PC 不采用向量表项“bit 0 置 1”的编码；不要混用这两个字段的规则。

损坏返回 PC、xPSR 或栈访问本身，还可能造成 INVSTATE、取指故障或 UNSTKERR；相关故障无法正常进入时可升级为 HardFault。故障状态和帧有效性必须结合判断，不能见到一个形似 `0xFFFFFFFD` 的 LR 就直接解引用帧内 PC。

来源：[PM0056 §2.1.1–2.1.3；§2.3.7](../来源/PM0056.md#src-pm0056-r7-exception-frame)；[§4.4.10 SCB_CFSR](../来源/PM0056.md#src-pm0056-r7-fault-evidence)；[Arm DDI0403E.b §B1.5.6 ReturnAddress，B1-590](https://documentation-service.arm.com/static/5f8fef3af86e16515cdbf816#page=590)、[§B1.5.8，B1-595～599](https://documentation-service.arm.com/static/5f8fef3af86e16515cdbf816#page=595)。
